# NuGet 供应链漏洞扫描

## 目标

识别项目依赖中的已知漏洞，并将组件漏洞与可能受影响的入口或功能域对齐。

## 输入

- `source_path`
- 可选：`route_mapping/routes_{timestamp}.md` 与 `route_mapping/params_{timestamp}.md`（如已由 `dotnet-route-mapper` 生成，用于把受影响组件映射到统一入口与 `route_id`）
- 可选：`auth_audit/auth_mapping_{timestamp}.md`（如需把受影响组件和匿名/P0/P1 入口一起排序）
- 可选：`offline_audit_report`（用户注入的离线扫描报告——`dotnet list package --vulnerable` 输出；提供时解析（包,版本,漏洞ID,严重级）与本地依赖清单 join 并入结论，产物单独列出「来自注入报告的命中」与「来自内置知识的命中」两组）

## 必做项

- 解析依赖包名与版本
- 识别影响版本区间
- 输出代码中直接引用该组件的位置
- 推断可能受影响的 route_id 或入口类型

## 失败与降级分支（强制）

| 触发条件 | 一线处理 | 仍失败的兜底 |
|---|---|---|
| 依赖文件缺失（`*.csproj`/`Directory.Packages.props`/`packages.config`） | 继续扫描其余依赖清单文件并记录缺失清单 | 输出 `⚠️依赖清单不完整`，结论降级为 PARTIAL |
| 版本区间无法解析（浮动版本、条件引用） | 记录原始版本表达式并尝试标准化解析 | 以 `待验证` 标记进入风险池，不输出“已确认受影响” |
| 漏洞库无匹配结果或版本映射不一致 | 记录组件与版本并保留“无确证”说明 | 输出 `环境依赖/需外部情报补证`，禁止写“无风险” |
| 包在代码中无直接引用 | 先标记为间接依赖并继续分析传递依赖 | 无法闭合时标记 `SINK_SUSPECT`，待 route-tracer/framework 交叉补证 |

🔴 **STOP：触发任一兜底分支时，禁止输出“完全无风险”结论。**

## 资源引用与可达性校验（强制）

- 必引共享索引：`skills/shared/DOTNET_AUDIT_GRABBER_INDEX.md`（抓手来源）与 `skills/shared/EVIDENCE_POINT_IDS.md`（证据口径）。
- 输出口径校验：落盘路径与命名必须对齐 `skills/shared/IO_PATH_CONVENTION.md`，不得自定义偏离目录。
- 证据一致性校验：若引用分级结论，需与 `skills/shared/SEVERITY_RATING.md` 保持一致。
- 可达性检查：提交前至少确认一次关键引用文件可访问（例如 `DOTNET_AUDIT_GRABBER_INDEX.md`、`IO_PATH_CONVENTION.md`）。

## 实测用例与通过标准（强制）

- 每个 skill 至少维护 2 个典型测试用例（happy path + 一条复杂场景），并在结果中标注用例 ID。
- 每轮评估至少 1 条用例执行 `full_test`；若受限只能 `dry_run`，必须记录 `dry_run_reason` 与补测计划。
- 通过标准至少同时满足：`意图达成`、`关键证据命中`、`输出格式合规`；任一不满足不得给出“通过”。

## 整体架构与冗余控制（强制）

- 章节组织必须保持三层骨架：`输入约束` → `执行步骤` → `输出与验收`，不得缺层或跨层混写。
- 单段建议不超过 6 行；同义规则禁止重复出现两次以上，重复内容需合并到唯一真源章节。
- 禁止 AI 腔与空话衔接词堆叠（如“首先/其次/最后/综上/说白了/换句话说”）；发现即改为可执行语句。

## 质量门禁与评估一致性（强制）

- 产出前必须执行最小门禁自检：`输入完整性`、`关键证据命中`、`输出路径合法` 三项全部为 PASS。
- 若存在 `关键证据缺失`、`链路未闭合`、`consistency_check_status=BLOCKED` 任一条件，结论必须降级为 `BLOCKED`，禁止输出“确认可利用/可交付”。
- 报告中必须显式记录：`gate_status`、`blocked_reasons`、`recheck_action`，并与 `quality/*` 产物可回溯对齐。

## 不要做的事（反例黑名单）

| # | 反模式 | 为什么不要做 | 正确做法 |
|---|---|---|---|
| 1 | 只因“没命中漏洞库”就判定安全 | 情报缺失不等于无风险 | 明确标记“无确证”并保留补证入口 |
| 2 | 忽略传递依赖 | 二级依赖常是真实漏洞面 | 至少记录传递依赖和受影响路径 |
| 3 | 只报包名不报版本区间 | 无法用于修复与复现 | 必须给出受影响版本与当前版本 |
| 4 | 不对齐 route_id/功能域 | 无法进入 pipeline 风险排序 | 输出受影响入口或模块映射 |

## 工作流（输入→执行→输出）

1. 输入：读取 `source_path` 与上游产物（如 `route_mapping` / `route_tracer` / `framework_audit`），确认依赖可用且时间戳一致。
2. 执行：按“共享抓手索引 → 本专项枚举规则 → 证据点引用”顺序完成审计，记录命中点、证据链与未闭合路径。
3. 输出：按本文件“输出”章节落盘到约定路径，结论需标注 `已确认` / `⚠️待验证`，并附缺失证据清单。

## 检查点设计（强制）

- 🔴 **CHECKPOINT A（资产清单确认）**：必须确认 NuGet 依赖、版本与来源清单完整。
- 🔴 **CHECKPOINT B（漏洞匹配确认）**：必须确认 CVE/GHSA 匹配规则与证据来源。
- 🔴 **CHECKPOINT C（修复建议确认）**：必须确认修复版本与兼容性影响可落地。
- 🛑 **STOP**：若漏洞匹配依据不完整，禁止输出“无高危”结论。

## 可执行参数与输出模板（强制）

- 审计结论等级：`已确认` / `⚠️待验证` / `不适用`（三选一，禁止留空）。
- 证据最小集：至少包含 `入口点`、`可控参数`、`关键调用`、`安全边界`、`缺失证据` 五项。
- 输出文件命名：统一使用 `{topic}_{timestamp}.md`，并与 `IO_PATH_CONVENTION.md` 对齐。
- 禁止使用软化措辞：如“可能有风险/建议关注/视情况而定/大概率”等；证据不足时必须明确写 `⚠️待验证` 与下一步补证动作。

最小输出片段（可直接复用）：

```md
- 审计结论等级：已确认
- 证据最小集：入口点=...；可控参数=...；关键调用=...；安全边界=...；缺失证据=无
- 下一步动作：若存在缺口，补 trace_id=... 的参数传播证据
```

## 输出

- vuln_report/{project_name}_nuget_vuln_report_{timestamp}.md
- 产物头部必含 `knowledge_cutoff_date: {YYYY-MM-DD|unknown}`（内置知识声明截止日期，unknown 时伴「结论可能滞后」声明）与 `offline_report_source: {路径|none}`；无注入报告且无在线比对时必须声明「未做在线比对」。
- **字段级合规矩阵（2026-09-20，强制）**：`knowledge_cutoff_date` / `offline_report_source` 为**字面字段**必含——逐字命中方为合规；语义等价改写（如「知识截止日期」「离线报告来源」「数据时效声明」等替代表述）视为不合规，视同缺字段处理。
