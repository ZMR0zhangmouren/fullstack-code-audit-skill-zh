# 漏洞统一分级标准（.NET）

## 严重等级计算公式

```text
Score = R × 0.40 + I × 0.35 + C × 0.25
CVSS 映射 = Score / 3.0 × 10.0
```

若 C=0（不可利用），Score 必须归零，漏洞等级不得高于 L（Low），禁止按加权公式得出 M/H。

## 三维评分标准

### 可达性 (R)

- 3：无需认证，HTTP/Hub/GraphQL 直接可达
- 2：需要普通用户认证
- 1：需要管理员、内网或特定角色
- 0：不可达或 trace_status=UNRESOLVED

### 影响范围 (I)

- 3：RCE、任意文件写入、完全数据泄露、租户突破
- 2：敏感数据泄露、越权、部分任意读写、高价值业务影响
- 1：有限信息泄露、局部状态异常、低影响配置暴露
- 0：无实际安全影响

### 利用复杂度 (C)

- 3：低复杂度，单请求或低成本触发
- 2：中复杂度，需构造 payload、特定角色或多步操作
- 1：高复杂度，需要竞态、链式利用或严格环境条件
- 0：不可利用（触发 Score 归零规则）

## 等级映射

| 前缀 | Score 区间 | CVSS 3.1 |
| ---- | ---- | ---- |
| C | 2.70 - 3.00 | 9.0 - 10.0 |
| H | 2.10 - 2.69 | 7.0 - 8.9 |
| M | 1.20 - 2.09 | 4.0 - 6.9 |
| L | 0.10 - 1.19 | 0.1 - 3.9 |

## 定级枚举闭合（2026-09-20，强制）

- 定级枚举只允许 `C` / `H` / `M` / `L` 四值；任何产物（漏洞编号前缀、发现统计表、报告分级列、利用链最低等级）不得出现枚举外等级。
- 边界情形（介于两档之间、证据不足以上调但风险偏高）必须使用「升级通道注记」格式：`L（建议升 M，理由：…）`——枚举值仍为 `L`，括号内写明建议上调档位与具体理由。
- 禁止区间值模糊标注：`L-M` 为反例，不合规（凡写「L-M」「M~H」等区间值的统计表/报告行，必须改写为升级通道注记格式，如 `L（建议升 M，理由：…）`）。
- 升级通道注记不改动漏洞编号前缀与三维评分，仅作人工复核提示；上调落地须经复核并在证据链中补记理由。
- 统计分组按枚举值取值（2026-09-21）：一切统计表 / 计数 / 分档汇总按枚举值 `C` / `H` / `M` / `L` 分组；「升级通道注记」（如 `L（建议升 M，理由：…）`）不计入 M（也不计入任何建议目标档），只计入其枚举值本身（该例计入 L）。

## 漏洞编号规范

格式：{等级前缀}-{类型代码}-{序号}

类型代码建议（与 dotnet-audit-pipeline 漏洞编号规范章节对齐）：

- SQL / NOSQL / KQL / CMD / SSRF / XSS / DOMXSS / FILE / UPLOAD / WRITE / ARCHIVE
- REDIR / CRLF / XXE / DESER / TPL / SSTI / LDAP / EXPR / XPATH / SECOND / DESYNC
- AUTH / CSRF / SESS / CFG / CRYPTO / SUPPLY / LOGIC / FS / LOG
- PROTO：原型链污染（JS 特有）
- REDOS：正则拒绝服务（JS 特有）
- QUERY：非 SQL 查询语言注入（SOQL/OData/FetchXML 等）
- EXPORT：电子表格公式注入（CSV/Excel 导出解释边界）
- PROMPT：AI 提示注入（指令/数据边界跨越）

node 侧漏洞编号格式与既有 `{等级前缀}-{类型代码}-{序号}` 一致。

## 可利用性标注

| 标记 | 含义 |
| ---- | ---- |
| ✅ 已确认可利用 | 证据链闭合，执行点、可控性与前置条件均已成立 |
| ⚠️ 待验证 | 存在风险，但 trace 或关键证据不足 |
| ❌ 不可利用 | 有效防护成立或关键执行点无法到达 |
| 🔍 环境依赖 | 需依赖宿主环境、部署配置或外部组件条件 |
